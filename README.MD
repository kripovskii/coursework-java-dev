## 2. Правила нормоконтроля (СТО)

Нормоконтролер проверяет не гениальность кода, а соответствие стандартам оформления. Нарушение этих правил ведет к автоматическому возврату работы. Настройте Word один раз и не меняйте эти параметры.

- **Формат:** A4, печать на одной стороне.
- **Поля:** Левое – 30 мм, Правое – 10 мм, Верхнее и Нижнее – 20 мм.
- **Шрифт:** Times New Roman, 14 pt, черный цвет.
- **Абзац:** Выравнивание по ширине, отступ первой строки 1.25 см.
- **Интервал:** Одинарный (для 14-го шрифта).
- **Заголовки:** Arial Cyr, 15 pt, по центру (Содержание, Введение, Заключение, Список литературы, Приложение) или с абзаца (Заголовки и подзаголовки без отступа 1,25). **Без точки в конце и после нумерации.**
- **Отступы заголовков и подзаголовков:** Заголовки 12 пт (два интервала) до и после заголовка раздела, подзаголовки 6 пт до и после.
- **Нумерация:** Сквозная, арабскими цифрами, правый верхний угол. Титульный лист считается первым, но номер на нем не ставится, как и на странице с Содержанием.
- **Ссылки:** В тексте обязательно должны быть ссылки на все рисунки, таблицы и источники (например: `Как показано на рисунке 1.2` или `...в работе [15, с. 45]`).
- **Важно для оформления:** Добавить автоперенос текста и одинарный интервал, значение 0.
Заголовки с новой страницы, подзаголовки - нет.
- **Код в тексте:** Фрагменты кода в основной части или приложениях должны быть оформлены моноширинным шрифтом (например, Courier New, 12-14 pt) с правильными отступами.
- **Кол-во страниц:** минимальное кол-во страниц 40, если хотите можно больше.

## 3. Roadmap: Этапы написания работы

Разбиваем написание пояснительной записки на итерации, чтобы избежать аврала перед дедлайном.

### Этап 1: Инициализация (Недели 1-2)
- [ ] Выбрать и зафиксировать тему в Google Таблице.
- [ ] Составить и утвердить план (Оглавление): Введение, Глава 1 (Аналитика), Глава 2 (Проектирование и Разработка), Заключение, Список источников, Приложения, берем из примеров!!!!!!.
- [ ] Написать Введение (Актуальность, Цель, Объект, Предмет, 4-5 Задач).

### Этап 2: Аналитика и Проектирование (Недели 3-4)
- [ ] **Глава 1:** Написать аналитику. Сравнить технологии, обосновать выбор стека. Сделать сравнительные таблицы.
- [ ] **Глава 2 (начало):** Описать предметную область. Спроектировать архитектуру (добавить UML-диаграммы, ER-диаграммы БД, схему взаимодействия компонентов).

### Этап 3: Описание реализации (Недели 5-6)
- [ ] **Глава 2 (продолжение):** Описать процесс разработки. Привести ключевые фрагменты кода (алгоритмы, контроллеры, модели данных).
- [ ] Проверить, что в тексте есть ссылки на все рисунки (скриншоты интерфейса, диаграммы) и таблицы.

### Этап 4: Полировка и Нормоконтроль (Недели 7-8)
- [ ] Проверка текста на антиплагиат (цель: >70% оригинальности).
- [ ] Вычитка по чек-листу СТО.
- [ ] Оформление списка литературы (строго по ГОСТ, 15-20 источников).

## 4. Разработка продукта: Инженерные стандарты

Поскольку курсовая подразумевает создание реального веб-приложения, к коду и процессу разработки применяются профессиональные инженерные требования. Ваш GitHub-репозиторий — это лицо проекта.

### 4.1. Архитектура и Стек
- **Разделение ответственности:** Четко разделяйте Frontend (клиент), Backend (сервер) и Database. Не смешивайте логику представления с бизнес-логикой.
- **API:** Взаимодействие между клиентом и сервером должно осуществляться через REST API (или GraphQL). Все эндпоинты должны возвращать предсказуемые JSON-ответы с правильными HTTP-статусами (200, 201, 400, 404, 500).
- **База данных:** Схема БД должна быть нормализована (минимум до 3НФ). Используйте миграции для управления схемой, не создавайте таблицы вручную в продакшене.

### 4.2. Качество кода и Линтеры
- **Форматирование:** Настройте Prettier (или аналог) для единообразного стиля кода.
- **Статический анализ:** Подключите ESLint. Код не должен содержать критических предупреждений.
- **Чистый код:** Следуйте принципам DRY (Don't Repeat Yourself) и KISS (Keep It Simple, Stupid). Избегайте "магических чисел" (используйте константы), давайте переменным и функциям осмысленные имена.

### 4.3. Git и Контроль версий
- **Ветвление:** Не пишите весь код в ветке `main`. Создавайте отдельные ветки для фич (например, `feature/auth-module`, `fix/db-connection`).
- **Коммиты:** Используйте Conventional Commits. Сообщения должны отвечать на вопрос "Что сделано?".
  - *Правильно:* `feat: add user login endpoint`, `fix: resolve cors issue`, `docs: update API readme`.
  - *Неправильно:* `update`, `fix bug`, `123`.
- **История:** Делайте коммиты логическими блоками, а не по одной строке кода.

### 4.4. Конфигурация и Безопасность
- **.gitignore:** Это критически важный файл. В нем **обязательно** должны быть исключены: `node_modules/`, `.env`, `dist/`, `.idea/`, `.vscode/`, логи и кэши.
- **Секреты:** Никогда не коммитьте пароли, API-ключи, строки подключения к БД в код. Используйте переменные окружения (`.env` файл).
- **README репозитория:** В репозитории с кодом должен быть свой `README.md` с инструкцией по локальному запуску (как установить зависимости, как настроить `.env`, как запустить сервер и клиент).

### 4.5. Тестирование и Отладка
- **API:** Протестируйте все эндпоинты бэкенда через Postman или Swagger. Сохраните коллекцию запросов (можно приложить к работе как скриншоты в Приложения).
- **UI:** Проверьте адаптивность верстки на мобильных устройствах и планшетах.
- **Обработка ошибок:** Фронтенд должен корректно обрабатывать ошибки сети и сервера (показывать понятные пользователю сообщения, а не просто "падать").

## 5. AI Copilot: Гайд по промптам

Нейросети — это ваш младший разработчик и редактор. Но если дать плохое ТЗ, вы получите галлюцинации и 100% детект ИИ в антиплагиате.

**Анти-паттерн (Как не надо):**
> "Напиши введение для курсовой по веб-разработке."
*(Результат: вода, общие фразы, стиль школьного сочинения, палится антиплагиатом).*

**Промпт-фреймворк:** Роль + Контекст + Задача + Формат + Ограничения.

**Пример 1: Генерация структуры и плана**
> **Роль:** Ты — опытный Senior Web Developer и научный руководитель.
> **Контекст:** Я пишу курсовую работу на тему "Разработка веб-приложения для учета задач с использованием React и Node.js".
> **Задача:** Составь подробное оглавление курсовой работы. Оно должно содержать Введение, 2 главы, Заключение и Список литературы.
> **Ограничения:** В первой главе должен быть сравнительный анализ фреймворков. Во второй — описание архитектуры, БД и реализации API. Стиль заголовков: строгий, научно-технический.

**Пример 2: Научный рерайт (борьба с антиплагиатом)**
> **Роль:** Ты — профессиональный научный редактор.
> **Задача:** Перепиши следующий текст, повышая его научную плотность и уникальность.
> **Ограничения:** Используй научно-деловой стиль. Замени простые слова на термины. Сохрани исходный смысл.
> **Текст для рерайта:** [ВСТАВЬТЕ СЮДА ВАШ ЧЕРНОВИК]

**Пример 3: Рефакторинг кода**
> **Роль:** Ты — эксперт по чистому коду на JavaScript.
> **Задача:** Проведи рефакторинг следующего фрагмента кода контроллера.
> **Ограничения:** Раздели логику валидации и бизнес-логику. Добавь обработку ошибок через try/catch. Используй асинхронный подход.
> **Код:** [ВСТАВЬТЕ КОД]

**Правила безопасности при использовании ИИ:**
1. **Фактчекинг:** ИИ часто выдумывает несуществующие книги и статьи. Проверяйте все ссылки на источники.
2. **Детекция ИИ:** Не копируйте текст целиком. Всегда прогоняйте его через "научный рерайт" и добавляйте свои мысли.
3. **Код:** ИИ может написать уязвимый код. Всегда делайте ревью перед вставкой в проект.

## 6. Защита и Презентация

Презентация — это фронтенд вашего проекта. Она должна быть чистой, понятной и понятной.

**Структура слайдов (10-12 шт.):**
1. **Титульный:** Тема, ФИО, группа, руководитель.
2. **Актуальность:** 2-3 тезиса, почему это важно именно сейчас.
3. **Проблема:** Какую "боль" пользователя решает ваш продукт.
4. **Цель и задачи:** Кратко, тезисно (как во введении).
5. **Теория/Стек:** Диаграмма выбора технологий или сравнительная таблица.
6. **Архитектура:** Схема взаимодействия клиента, сервера и БД (обязательно).
7. **Практические результаты:** Скриншоты интерфейса, фрагменты сложного кода, ER-диаграмма.
8. **ДЕМОНСТРАЦИЯ:** Переключение на демонстрацию экрана (Live Demo) или воспроизведение заранее записанного видео работы приложения. Это самый важный момент защиты.
9. **Выводы:** Цель достигнута, задачи решены.
10. **Спасибо за внимание!** (Готов ответить на вопросы).

## 7. Финальный чек-лист

**По документации:**
- [ ] Тема и структура зафиксированы в Google Таблице.
- [ ] Все задачи из Введения закрыты в тексте глав.
- [ ] В тексте есть ссылки на все `Рисунок X.X` и `Таблицу X.X`.
- [ ] Список литературы содержит 15+ источников, оформленных по ГОСТ.
- [ ] Поля, шрифты (TNR 14), интервалы и отступы проверены по СТО.
- [ ] Титульный лист сверен с шаблоном из репозитория.

**По коду и продукту:**
- [ ] В репозитории есть `README.md` с инструкцией по запуску.
- [ ] Файл `.gitignore` настроен (нет `node_modules`, `.env` в коммитах).
- [ ] Код отформатирован, нет критических ошибок линтера.
- [ ] Приложение успешно разворачивается локально по инструкции из README.
- [ ] Презентация готова, Live Demo протестирован и работает без критических багов.

>[!TIP]
> Пишите работу итерациями. Сделали параграф или фичу -> показали мне -> получили правки -> закоммитили изменения. Это гарантирует высокую оценку и отсутствие стресса перед дедлайном. Если есть вопросы по оформлению — сначала откройте приложенные PDF-файлы. Если не нашли — смело пишите.

## 8. Рабочий процесс разработки

- Работа ведётся по Git Flow.
- Основная ветка: `main`.
- Ветка разработки: `develop`.
- Для новых задач создаются ветки `feature/*`.
- Для исправлений создаются ветки `fix/*`.
- Готовые изменения попадают в `develop` через pull request.
- Релизные изменения передаются в `main` только после проверки.

## Порядок работы

1. Создать ветку от `develop`.
2. Выполнить задачу в отдельном коммите или серии небольших коммитов.
3. Проверить результат локально.
4. Обновить файл с прогрессом.
5. Создать pull request в `develop`.
6. После ревью и проверки слить изменения.

## Фиксация прогресса

Прогресс фиксируется в отдельном файле.

- Вносить туда краткое описание выполненной работы.
- Указывать дату и статус задачи.
- Отмечать, что уже сделано и что осталось.
- Обновлять файл после каждого значимого изменения.

## Рекомендации по коммитам

- Один коммит — одно логическое изменение.
- Сообщения коммитов делать короткими и понятными.
- Не смешивать в одном коммите разные типы изменений.

## Проверка перед сдачей

- Убедиться, что проект собирается и запускается.
- Проверить, что все изменения находятся в нужной ветке.
- Просмотреть diff перед отправкой.
- Обновить документацию при необходимости.

## Структура работы

- `main` — стабильная версия.
- `develop` — основная ветка разработки.
- `feature/*` — новые функции.
- `fix/*` — исправления.
- отдельный файл — журнал прогресса.
